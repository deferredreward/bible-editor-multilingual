# UI localization

The Bible Editor chrome (buttons, tooltips, dialogs, toasts, banners) is
localized with [i18next](https://www.i18next.com/) + `react-i18next`. Scripture
content itself is project data, not UI — this doc is only about the interface.

## Where things live

| Path | What |
| --- | --- |
| `web/src/i18n/index.ts` | i18next init + the `UI_LANGUAGES` registry (code, native label, `dir`) |
| `web/src/i18n/locales/en.json` | **Source of truth** — every key the UI can request |
| `web/src/i18n/locales/<code>.json` | One file per language, mirroring `en.json` |
| `web/src/i18n/coverage.json` | Which locales gate CI, the accepted-gap baseline, and native-review status |
| `scripts/check-i18n.mjs` | Completeness checker — runs in CI on every PR |
| `scripts/i18n-extract-missing.mjs` | Dump a locale's missing keys + English source, ready to hand to a translator |
| `scripts/i18n-apply.mjs` | Merge translated key maps back into a locale; prune stale keys |

Keys are namespaced (`common`, `topbar`, `translation`, `preferences`, `export`,
`importDialog`, `questions`, `words`, `rail`, `sync`, `shell`, `pipeline`,
`noteCard`, `aligner`, `lanes`, `logos`, `articles`) and
referenced in code as `t("ns.key")`. `en` is the `fallbackLng`, so a missing
key in another locale silently renders English rather than a raw `ns.key` —
which is why the checker exists: fallbacks hide gaps.

## Adding a language

1. **Register it** in `web/src/i18n/index.ts`:
   - `import xx from "./locales/xx.json";`
   - add `xx: { translation: xx }` to the `resources` block;
   - add a row to `UI_LANGUAGES` with the **native** label and the correct
     `dir` (`"rtl"` for right-to-left scripts — Arabic, Farsi, Urdu, Hebrew;
     `"ltr"` otherwise). `dir` drives full mirroring: `document.dir`, the MUI
     theme direction, and the emotion RTL cache all key off it (see `main.tsx`).
2. **Copy the full key set** from `en.json` into `web/src/i18n/locales/xx.json`
   — same namespaces, same keys, same nesting.
3. **Translate the values.** Two hard rules:
   - **Preserve `{{var}}` placeholders exactly** (`{{book}}`, `{{count}}`,
     `{{message}}`, …). They are interpolated at runtime; renaming or dropping
     one breaks the message.
   - **Keep Latin resource tokens literal:** `ULT`, `UST`, `UHB`, `UGNT`,
     `Door43`, `DCS`, `TW`, `TN`, `TQ`, `TWL`, and key hints like `Ctrl+F`.
     These are proper names / shortcuts, not words to translate.
4. **Get the plurals right.** i18next resolves a base key through suffixed
   variants using the CLDR plural rules for that language (via
   `Intl.PluralRules`). Provide exactly the categories your language uses:

   | Language(s) | Categories | Suffixes to supply |
   | --- | --- | --- |
   | id, th, zh, ja, ko | `other` | `_other` |
   | es, fr, pt | `one, many, other` | `_one _many _other` |
   | hi, sw, ne, bn, ur, fa, tr | `one, other` | `_one _other` |
   | ru, uk (Slavic) | `one, few, many, other` | `_one _few _many _other` |
   | ar (Arabic) | `zero, one, two, few, many, other` | all six |

   The 19 plural base keys today are `aligner.acceptSuggestions`,
   `lanes.attrPeople`, `lanes.attrYouPlusOthers`, `noteCard.timesSaved`,
   `pipeline.pipelinesRunning`, `preferences.renderingCount`, `shell.colCount`,
   `shell.editLeftUnaligned`, `sync.conflict`, `sync.discardConfirmTitle`,
   `sync.quarantinedDrafts`, `sync.queuedLocally`, `sync.resolveConflicts`,
   `sync.savingTooltip`, `sync.unsavedEditsClickToJump`,
   `sync.unsavedEditsColon`, `topbar.status.conflictsLabel`,
   `topbar.status.failedLabel`, `topbar.status.issuesToCleanUp`.
   (`en.json` is the authority: a base counts as plural iff en supplies ≥2
   distinct CLDR suffixes for it.)

   > **Note on Farsi (fa) and Urdu (ur):** despite being written in the
   > Arabic script, CLDR classifies both as **one/other** — not the six-way
   > Arabic split. `Intl.PluralRules` (what i18next uses) only ever requests
   > `_one`/`_other` for them, so extra `_zero/_two/_few/_many` keys would be
   > dead weight. Only `ar` itself uses all six.

5. **Verify:** `node scripts/check-i18n.mjs`. It must report your locale as
   complete (exit 0).

## What the checker enforces

`node scripts/check-i18n.mjs` compares every `locales/*.json` (except `en.json`)
against `en.json` and, per locale, reports:

- **MISSING** — base keys in `en.json` absent from the locale. Plural-aware: any
  suffixed variant (`_one`, `_other`, `_zero`, `_two`, `_few`, `_many`)
  satisfies its base key.
- **PLURAL categories missing** — a plural base is present but lacks a category
  that `Intl.PluralRules(<code>)` will actually request for that language (e.g.
  a Russian file with `_one/_other` but no `_few`/`_many`).
- **STALE** — keys in the locale that no longer exist in `en.json` (typos,
  renamed keys, leftover stub `_comment`s).
- **ORPHAN** — a `t("ns.key")` literal in `web/src` that `en.json` doesn't
  define. `tsc` can't catch this; i18next just renders the raw key at runtime.

### Tiering — why this gates CI without demanding 13 translations

Translating every new UI string into all 13 languages is not a reasonable ask
of every PR, so `web/src/i18n/coverage.json` splits locales into two tiers:

| Tier | Locales | Rule |
| --- | --- | --- |
| **gated** | `ar` | Must be 100% complete. Any missing key, missing plural category, or **value left identical to English** fails. |
| **baseline** | the other 12 | Known gaps are recorded and tolerated. Only a **new** gap fails. |

So a PR that adds a UI string must supply English **and Arabic**, and nothing
else. The other 12 locales can't get *worse* — deleting a translation or adding
an untranslated key fails just as loudly — but their existing backlog never
blocks anyone.

**STALE keys and code ORPHANs fail for every locale in both tiers.** Neither is
untranslated work; both are rot, and both are cheap to fix.

### Why gated locales are checked on values, not just keys

Key presence is a weak signal: copying `en.json` to `xx.json` would report 100%
complete while rendering an entirely English UI. So for **gated** locales the
checker also fails on any value byte-identical to `en.json`.

Some values *should* match English — brand names (`OpenAI`, `Aquifer`,
`unfoldingWord`), resource proper names (`translationNotes`), short badge codes
(`SH`, `TCM`, `AI`), symbols (`—`, `→`), and strings that are nothing but
placeholders (`{{role}} ({{source}})`). Those keys are listed in
`sameAsEnglish` in `coverage.json`. Add a key there **only** when the English
form is genuinely correct in that language — never to silence the check.

This rule is deliberately gated-only. Backlog locales are full of untranslated
values by definition; `baseline` governs them.

> Still not covered: a *wrong* or low-quality translation. Only a native
> speaker catches that. See Translation quality below.

When you translate a batch (or deliberately accept a new gap in a baseline
locale), re-record the baseline:

```sh
node scripts/check-i18n.mjs --update-baseline
```

The baseline list should only ever shrink. It is a ratchet against rot, not a
to-do list we intend to keep.

**Promoting a locale to `gated`** means every future PR must translate into it.
Only do this once the locale is complete *and* we intend to ship it to a client.

### Translating a backlog locale

```sh
node scripts/i18n-extract-missing.mjs fr /tmp/fr-missing.json   # keys + English source
# ...translate the values in that file, keys unchanged...
node scripts/i18n-apply.mjs fr /tmp/fr-missing.json             # merge back, en key order
node scripts/check-i18n.mjs --update-baseline                   # shrink the baseline
```

`i18n-apply.mjs` never overwrites an existing value, so a re-run is safe and a
translator can't silently clobber reviewed text. The extractor expands plural
bases into exactly the CLDR categories the target language needs (all six for
Arabic), seeded with the English text so the translator sees real source.

## Translation quality

**Every locale except `en` is machine-drafted and has had no native-speaker
review**, including `ar`. Per-locale status lives in the `review` block of
`web/src/i18n/coverage.json` — record a native pass there.

Coverage and quality are separate axes:

- **Coverage** — `ar` is complete: every key present, every value actually in
  Arabic (bar the 20 allow-listed brand/code/symbol strings), all six CLDR
  plural categories. The other 12 sit at roughly 65% (see `baseline`); a missing
  key falls back to English at runtime, so those locales render a mix of their
  language and English.
- **Quality** — machine-checked: placeholders, plural categories, and
  not-still-English. **Not** machine-checked: whether the Arabic is *right*.
  Wording, tone, register, and terminology consistency need a native pass.

**Do not present a language to a client before it has had a native pass.**
Arabic is the first client language, which is why it is the only gated locale.
